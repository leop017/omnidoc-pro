# v0.2.5 — 0.2.x 审计回归修复（URL 抓取 charset + 0-chunk 退出码）

**OmniDoc Pro** v0.2.5 是针对「0.2.0→0.2.4 更新链」的一次性审计与回归修复。基于对 0.2.0→0.2.4 五个版本变更的逐条源码复核 + 一次性真实探针，筛出 **2 条对用户可观测的功能回归** 并全部修复，其余 5 条疑似问题经探针证实为理论边角或文档与行为一致（详见下文"未修项"）。全部 373 个测试通过。

## 🌐 高严重度：0.2.1 SSRF 重写让正常 URL 抓取崩溃（charset API 错配）

### 问题

0.2.1 把 URL 抓取从 `requests` 重写为 urllib3 `HTTPConnectionPool`（IP 钉扎 + 手动跟重定向 + 每跳 SSRF 复核）。但 `markitdown_engine.py:193` 取 body 时仍调 `resp.headers.get_content_charset()` —— 这是 **requests.Response 的专有 API**，urllib3 返回的 `HTTPResponse` 的 `.headers` 是 `HTTPHeaderDict`，**没有这个方法**：

```python
AttributeError: 'HTTPHeaderDict' object has no attribute 'get_content_charset'
```

任何公网 URL 的 `convert_document` 都会抛这个异常，被 `except Exception` 兜底成 `ERROR` 状态 + 占位 markdown。**URL 抓取功能在 0.2.1 起实际不可用**。

**探针验证**：直接调用 `_fetch_via_ip("http://example.com/")`（不 mock）实测：DNS 解析 + SSRF 校验都正确放行（`private_blocked=False`），但取 body 时抛 `AttributeError`。372 条现有测试未抓到，因为 `test_public_url_path` mock 掉了整个 `_fetch_safe_html`，urllib3 返回值从未被真实测试覆盖。

### 修复

新增 `_charset_from_ctype(content_type)` 辅助函数（8 行）：用正则从 `Content-Type` 头解析 `charset=` 参数（大小写不敏感，支持带连字符的 token 如 `ISO-8859-1`），无 charset 参数或空头时回退 UTF-8。193 行改为：

```python
charset = _charset_from_ctype(resp.headers.get("Content-Type", ""))
return resp.data.decode(charset, errors="replace")
```

## 🧩 高严重度：0.2.2 B4「0-chunk 降级」在 CLI 退出码上没落地（success 语义）

### 问题

0.2.2 B4 把"0-chunk 从 OK 降到 DEGRADED"作为修复落地，但 `document.py` 的 `success` 属性定义为：

```python
status in (OK, DEGRADED) and (markdown or chunks)
```

0-chunk 时 `chunks` 为空，只要 `markdown` 非空（RAG 场景下几乎必非空），`success` 仍为 True → CLI `cli.py:189-190` 的 `if not any(r.success): raise typer.Exit(code=1)` 仍 exit 0。**用户开 RAG 但拿到 0-chunk（空索引），CLI 却报告成功** —— B4 的修复在用户可观测的退出码上完全没起作用。

### 修复

`DocumentResult` 新增 `rag_failed: bool = False` 字段；`success` 属性首行加 `if self.rag_failed: return False`。`pipeline._chunk` 的 0-chunk 降级分支（原 `pipeline.py:143-153`）额外置 `result.rag_failed = True`。语义：**chunking 启用但 0-chunk = RAG 功能失败，无论 markdown 是否非空，`success` 恒为 False**，CLI 真正 exit 1。

## 📌 未修项（经探针证实为理论边角 / 文档一致，搁置）

以下 5 条在审计中识别，但经真实代码路径与探针确认**当前无可复现路径**或**行为与文档一致**，不在 0.2.5 修复：

- **`_sync_written_files` "恰好 1 个 .md" 判据脆弱**（0.2.3）：语义是"文件数 == 1 才同步"，对"某次转换恰好只写 1 个 .md 但内容是整篇拼接"的边角脆弱。方向对、实现脆弱，但当前行为正确。
- **`make_chunk` 只 copy `sheets` 一个嵌套 key**（0.2.4）：打地鼠式修复，对其它嵌套 key（`images`/`tables` 等）未覆盖，但当前无引擎填这些 key。
- **重分块错位（A2 + B1 叠加）**：`LlmEnhancer` 改写文本后保留旧 `elements`，旧偏移对新文本失效；但当前**没有任何引擎填 `elements`**（全走空 elements 的 text-reparse fallback），所以今天不能在生产路径复现，属"未来引擎填 elements 时"的预留缺陷。
- **写盘失败 `output_paths` 置空**（0.2.4）：WebUI 走 `elif r.markdown` 兜底，CLI 的 `--export-chunks` 在写盘失败时 `used` 集合可能重名，边角、低严重度。
- **`SentenceChunker` 前导空白 offset**（0.1.7）：`chunk()` 内先 `.strip()` 再算 offset，offset 相对原始文本会偏移。但 docstring 已声明"byte offsets into the original (stripped) source text"——行为与文档一致，非 bug。
