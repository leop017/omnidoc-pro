# v0.3.1 — LLM 增强返回新对象时的 re-chunk 一致性修复

**OmniDoc Pro** v0.3.1 是 1 项针对 `ProcessingPipeline` 的 re-chunk 一致性修复。当增强器按 `EnhancerInterface` 契约返回一个**新的** `DocumentResult`（而非原地修改并返回原对象）时，旧的 re-chunk 守卫 `enhanced is result` 恒为 `False`，导致增强后的富化文本永远不会触发 re-chunk，分块与最终文档内容脱节。本轮修复让 re-chunk 守卫同时覆盖"原地修改"与"返回新对象"两条契约路径。

## 🔧 修复清单（1 项）

### 1. 🔄 `ProcessingPipeline.run()`：re-chunk 守卫兼容"返回新对象"路径（pipeline.py）

**问题**：`run()` 中 re-chunk 的守卫条件写成了 `if enhanced is result and ...`。实际 `LlmEnhancer` 是原地修改并 `return result`（`enhanced is result` 恒为 True），所以该分支能正常触发；但 `EnhancerInterface` 契约允许增强器**返回一个全新的 `DocumentResult`**（`enhanced is not result`），此时守卫恒为 False，re-chunk 永远不会执行，最终返回的对象仍带着增强前的 chunk，与富化后的 Markdown 文本脱节。

**修复**：把守卫重写为"对比增强前 Markdown 快照与最终对象 Markdown，文本有变化且存在 chunk 就 re-chunk"；若增强器返回了新对象，先 `result = enhanced` 重绑定，再对实际承载富化文本的对象执行 `_rechunk_if_stale`。原地修改路径行为完全不变（新分支只在 `enhanced is not result` 时生效），全量回归 `395 passed` + `6 subtests passed` 基线不回退。

## 🧪 验证

- **完整回归**：`395 passed` + `6 subtests passed`（基线不回退）。
- **行为抽查**：原地修改的 `LlmEnhancer` 行为不变；构造"返回新对象"的增强器，re-chunk 现正确触发且新 chunk 落到承载富化文本的对象上。
