# v0.3.4 — 三项零风险缺陷修复（Excel 增强 Markdown 列对齐 / 零诊断 ERROR / URL 重定向 scheme 防护）

**OmniDoc Pro** v0.3.4 包含 3 项经全量源码审计、实测复现并回归验证的零风险缺陷修复。每项修复均配套回归测试，全套测试 **404 passed**。

## 🔧 修复清单（3 项）

### 1. 🧩 `ExcelBuilder._generate_md_via_html`：≥2×2 合并单元格腿跳过导致列错位（_excel.py）

**问题**：增强 Markdown 路径（`output_fmt="md"` 且 `enhanced_md=True`）中，`_generate_md_via_html` 用 `row_spans` 记录并跳过合并单元格的"内部腿"（`r≥1 且 c≥1`）。但 Markdown 表格**没有** `rowspan`/`colspan` 属性——每个合并腿本应渲染为一个空占位 `<td>` 以保住列对齐；被跳过后整行少一个单元格，后续列整体左移。

**真实现象**（`A1:B2` 合并 + 第 3 列 `C3/c3_2/c3_3`）：

```
# 修复前（错误）
| H1 |  | C3 |       ← 3 列 ✓
| --- | --- | --- |
|  | c3\_2 |      ← 仅 2 列 ✗，c3_2 错位到第 2 列
|  |  | c3\_3 |   ← 3 列 ✓

# 修复后（正确）
| H1 |  | C3 |
| --- | --- | --- |
|  |  | c3\_2 |   ← 3 列 ✓，c3_2 落在第 3 列
|  |  | c3\_3 |   ← 3 列 ✓
```

**修复**：删除该函数内 `row_spans` 的标记与跳过逻辑，让每条腿（含主格）都走"非主格 → `&nbsp;` 空占位"分支。修复后：
- 2×2 场景全部行保持 3 列对齐；
- rowspan-only / colspan-only / 无合并表输出**逐字节不变**；
- 与同文件 HTML 路径 `_build_html_table` 的语义（腿渲染空占位）一致。

### 2. 🔍 `ExcelBuilder.build`：请求的工作表全部缺失时产生零诊断 ERROR（_excel.py）

**问题**：`build()` 的"空表早返回"在 `skipped` 种子逻辑之前执行。当调用方通过 `sheets=["Nope"]` 请求一个不存在的工作表时，`load_sheets` 过滤后 `all_sheets` 为空，触发早返回 `{"sheets": [], "errors": [], "skipped": [], ...}`——`skipped` 未被填充。下游 `DeepEngine._result_multi` 据此返回 `status=ERROR` 且 `errors=[]`、`warnings=[]`，即代码注释里明确要避免的"零诊断 ERROR"：调用方只能看到失败、看不到原因。

**修复**：把 `skipped` 种子逻辑移到空表早返回之前；早返回时带上 `skipped` 与结构化 `metadata`（与正常路径一致）。纯增量诊断信息，成功路径行为完全不变。

### 3. 🔒 `markitdown_engine._fetch_safe_html`：URL 重定向未按跳校验 scheme，`ftp://` 被静默跟随（markitdown_engine.py）

**问题**：`_fetch_safe_html` 对每一跳都做 DNS 解析 + 私有 IP 校验（防 SSRF），但**不校验 scheme**。模块文档明确"仅允许 `http://` 与 `https://`"，但 scheme 检查只在入口 `_is_safe_url` 做了一次。当服务端 `302` 重定向到 `ftp://` 时，`_fetch_via_ip` 按 `scheme == "https"` 判断走 HTTPS，否则一律当 HTTP（端口 80）抓取——`ftp://` 被静默当作 HTTP 请求跟随，与文档契约矛盾。

**修复**：在重定向循环每跳开头加 `urlparse(current).scheme in ("http", "https")` 校验，非 http(s) 直接 `raise ValueError`。与现有每跳 IP 校验同构。重定向到非 http(s) 的目标本来就不可能被 HTML→md 成功转换，收紧后无任何合法场景受损。
