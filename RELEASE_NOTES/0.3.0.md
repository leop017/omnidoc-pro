# v0.3.0 — WebUI 并发批量转换防护（URL 输入框 scheme 校验 + rag_failed 状态提示）

**OmniDoc Pro** v0.3.0 是 WebUI 并发/批量场景下的 2 项防护修复。每次转换可能同时处理多个来源（多文件上传 + 多 URL），本轮修复确保批量与并发路径下的输入语义清晰、结果状态诚实，全量回归 `395 passed` + `ruff All checks passed` 基线不回退。

## 🛡️ 修复清单（2 项）

### 1. 🌐 WebUI：URL 输入框只接受 http(s) 网页地址（webui.py）

**问题**：`_on_convert` 把 URL 框里的每一行原样塞进 `sources`，不做任何 scheme 校验。本地文件路径（如 `C:\test\report.docx`）或 `file://`、`ftp://` 等条目会直接进入 sources；路由器对"无 `://` 且扩展名受支持"的串走 Deep Engine，Deep Engine 会直接读服务器本地文件系统。默认 WebUI 绑 `127.0.0.1` 风险有限，但一旦加 `--share` 暴露公网，恶意用户可借 URL 框读服务器任意文件。

**修复**：`_on_convert` 对每条 URL 提取 scheme，只放行 `http` / `https`；其余条目收进 `rejected_urls` 并跳过。URL 框只有非法条目且无其他来源时，返回专用 Markdown（`_url_rejected_markdown`）明确提示"请改用左侧文档上传框处理本地文件"。合法 http(s) 与本地文件上传路径行为完全不变。

### 2. 📊 WebUI：分块失败（rag_failed）状态栏明确提示（webui.py）

**问题**：`pipeline._chunk` 在"分块启用但产生 0 chunks"时置 `result.rag_failed = True`、状态 DEGRADED，但 `result.markdown` 仍然存在。`_write_downloads` 只看 `r.markdown` 是否非空就生成 `.md` 下载，`_write_chunks` 因 `chunks` 为空静默跳过——用户拿到 Markdown 文件，却缺少 `chunks.jsonl`，且状态栏只写 `状态=degraded`，无法区分"降级"与"分块失败"。`DocumentResult.rag_failed` 注释明确要求调用方（含 WebUI download gating）把它当作功能性失败。

**修复**：状态行构建处，当 `r.rag_failed` 为 True 时追加 `· ⚠️ 分块失败（无 RAG chunks，已生成 Markdown 但未产出分块文件）`。不阻止下载（Markdown 内容本身有价值），仅补齐状态提示，零行为变更。
