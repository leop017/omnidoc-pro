# v0.3.8 — 零风险修复：URL 抓取 charset 解析（带引号 / 未知编码）

**OmniDoc Pro** v0.3.8 包含 2 项零风险缺陷修复，均集中在 MarkItDown 引擎的网页抓取路径。全套测试 **410 passed**（404 基线 + 6 条新增回归用例），`ruff check .` 全绿。

## 🔧 修复清单（2 项）

### 1. 🌐 `Content-Type` 带引号 charset 未被识别，GBK 网页被误解码为乱码

**问题**：
- [`omnidoc/engines/markitdown_engine.py`](omnidoc/engines/markitdown_engine.py) 的 `_charset_from_ctype()` 使用正则 `charset=([\w-]+)` 解析响应头。
- 该正则只匹配**裸 token** 形式，无法匹配 RFC 2616 §4.1.2 明确允许的 quoted-string 形式 `charset="gbk"` / `charset='gbk'`。
- 后果：服务端以带引号形式声明 charset 时（.NET `HttpContentHeaders`、部分 Java 框架的默认行为），解析失败静默回退 UTF-8 → **GBK 中文网页输出乱码**。

**实测**（修复前）：

| Content-Type | 修复前 | 修复后 |
|---|---|---|
| `text/html; charset=gbk` | `gbk` | `gbk`（不变） |
| `text/html; charset="gbk"` | `utf-8` ❌ | `gbk` ✅ |
| `text/html; charset='utf-8'` | `utf-8`（巧合正确） | `utf-8`（不变） |
| `text/html; charset= "windows-1252"` | `utf-8` ❌ | `windows-1252` ✅ |
| `text/html;charset=iso-8859-1` | `iso-8859-1` | `iso-8859-1`（不变） |
| `text/html` / `""` | `utf-8` | `utf-8`（不变） |

**修复**：
- 正则改为 `charset=\s*["\']?([\w-]+)["\']?`，容忍 `=` 后的合法空白与可选的单/双引号。

**风险 = 0 的论证**：
- 纯正则扩展，**不新增分支、不改变任何已有匹配结果**（所有无引号形式的返回值完全一致）；
- 已有测试 [`test_fetch_via_ip_extracts_charset_from_content_type`](tests/test_markitdown_engine.py) 的 6 条断言全部使用无引号形式，修复后逐条不变；
- 该测试的 docstring 原本就声明 "support both quoted and bare tokens" —— 本次修复是让**实现追平已有契约**，而非新增行为。

### 2. 💥 服务端声明未知 codec 时 `LookupError` 击穿，整条 URL 转换由 DEGRADED 退化为 ERROR

**问题**：
- `_fetch_safe_html()` 末尾执行 `resp.data.decode(charset, errors="replace")`。
- `errors="replace"` 只能兜住 `UnicodeDecodeError`；当服务端声明的 codec **当前 Python 不认识**时（如拼写错误 `charset=foobar`、或老旧私有编码名），异常在 **codec 查找阶段**抛出 `LookupError`，解码器根本没启动，`errors=` 完全无效。
- 后果：整个网页抓取抛异常 → 转换状态从"降级继续（DEGRADED）"恶化为"彻底失败（ERROR）"，用户在 UI 上只看到一个无内容的错误页。

**实测**（修复前）：

```
Content-Type: text/html; charset=nosuchcodec
-> LookupError: unknown encoding: nosuchcodec
-> _fetch_safe_html 抛出 → 整条 URL 转换 ERROR
```

**修复**：
- 将 `decode` 包入 `try/except LookupError`，回退到 `utf-8` + `errors="replace"` 尽力解码。

**风险 = 0 的论证**：
- `try/except` 只覆盖**新增**的失败路径（未知 codec），此前该路径必然抛异常，无任何既有行为依赖它；
- 正常路径（已知 codec）走原分支，字节序列与返回值逐字节一致；
- 符合该模块既有的 "graceful degradation" 设计意图（SSRF 防护、scheme 校验、binary 嗅探等均为降级而非抛错）。
